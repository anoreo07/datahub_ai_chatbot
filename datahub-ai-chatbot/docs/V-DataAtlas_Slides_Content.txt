SLIDE 3 — GIẢI PHÁP SẢN PHẨM (PRODUCT SOLUTION)
────────────────────────────────────────────────────────────────────────────────

TIÊU ĐỀ:
  V-DataAtlas: Trợ lý AI được neo chặt vào Catalog dữ liệu thực

SO SÁNH TRƯỚC / SAU:

  CÁCH CŨ (Không có V-DataAtlas):
    Người dùng hỏi LLM
    → LLM suy đoán dựa trên dữ liệu huấn luyện
    → Câu trả lời mơ hồ, có thể sai schema
    → Người dùng không biết tin tưởng hay không
    → Phải tự mở DataHub để kiểm tra lại

  V-DATAATLAS:
    Người dùng hỏi bằng ngôn ngữ tự nhiên (tiếng Việt/tiếng Anh)
    → Hệ thống hiểu ý định (Intent Classification)
    → Phân giải tên bảng ra URN chính xác (Entity Resolution)
    → Đọc thẳng dữ liệu từ PostgreSQL Catalog (Structured Retrieval)
    → Câu trả lời chính xác + trích dẫn nguồn rõ ràng
    → Người dùng nhìn thấy bằng chứng cụ thể (Evidence Panel)

ĐIỂM KHÁC BIỆT CỐT LÕI:
  • Câu trả lời luôn có nguồn gốc từ catalog có cấu trúc
    — không phải từ "trí tưởng tượng" của AI
  • Hai nhánh xử lý:
    [1] Structured Metadata Retrieval (PostgreSQL): deterministic, 8–15ms
    [2] Semantic RAG (OpenSearch): tìm kiếm ngữ nghĩa, 35–70ms
  • Hệ thống tự động chọn nhánh phù hợp với loại câu hỏi

CÂU CHỐT:
  "Câu trả lời có trích dẫn — bạn biết thông tin đến từ đâu."

SLIDE 5 — KIẾN TRÚC TỔNG QUAN (HIGH-LEVEL ARCHITECTURE)
────────────────────────────────────────────────────────────────────────────────

TIÊU ĐỀ:
  Kiến trúc 4 tầng — Từ câu hỏi đến câu trả lời

4 TẦNG KIẾN TRÚC:

  TẦNG 1 — FRONTEND (Next.js 16.3 / TypeScript / React 19)
    • Chat UI + SSE Streaming (phản hồi từng token, không chờ đợi)
    • Lineage Graph tương tác (React Flow — kéo thả, zoom)
    • Evidence Panel hiển thị nguồn tài liệu
    • 6 Action Buttons và Suggestion Chips

  TẦNG 2 — BACKEND & AI ENGINE (FastAPI / Python / Async)
    • ChatService — điều phối toàn bộ luồng xử lý
    • Intent Classifier — phân loại ý định câu hỏi
    • Entity Resolver — phân giải tên bảng ra URN
    • Query Planner (DAG) — lập kế hoạch truy vấn phức hợp
    • Thinking Mode — lập kế hoạch suy luận có cấu trúc
    • Answer Generator — tổng hợp câu trả lời qua LLM

  TẦNG 3 — SECURITY & GOVERNANCE
    • JWT HS256 Authentication
    • 5 RBAC Domain Roles
    • 884 Entity ACLs (áp dụng tại mức SQL WHERE clause)
    • Prompt Injection Detection + Guardrails

  TẦNG 4 — DATA & PERSISTENCE
    • PostgreSQL 16    — 9,067 thực thể catalog
    • OpenSearch 2.15  — 21,196 vector chunks
    • Redis 7          — Cache & Message Queue
    • DataHub GMS      — GraphQL API (nguồn đồng bộ)
    • Fireworks AI     — LLM + Vision (Qwen/Llama)
    • Ollama           — Embedding nomic-embed-text (768 chiều)

CƠ CHẾ ĐẶC BIỆT:
  1. STREAMING REAL-TIME: Phản hồi theo từng token — TTFT: 450–850ms
  2. DUAL RETRIEVAL: Structured (8–15ms) + Semantic (35–70ms)
  3. FAILOVER: DataHub lỗi → tự chuyển sang PostgreSQL local
  4. CONVERSATION MEMORY: Nhớ "bảng này", "nó" từ lượt hỏi trước

SLIDE 6 — 6 CHỨC NĂNG CỐT LÕI (6 CORE ACTIONS)
────────────────────────────────────────────────────────────────────────────────

TIÊU ĐỀ:
  Sáu điều người dùng có thể làm ngay hôm nay

ACTION 1 — SEARCH DATASET (Tìm kiếm & Khám phá Metadata)
  Người dùng nói: "Cho tôi xem schema bảng account_use_vehicle"
  Hệ thống làm:
    • Phân giải "account_use_vehicle" → URN chính xác trong catalog
    • Đọc danh sách cột, kiểu dữ liệu, owner, domain, tags
    • Trả về bảng schema có cấu trúc + thông tin liên quan
  Kết quả: URN, 8 cột kiểu STRING, 1 upstream từ AWS Glue,
           chủ sở hữu: data-team@company.vn

ACTION 2 — GENERATE SQL (Sinh câu lệnh SQL theo schema thực)
  Người dùng nói: "Viết SQL lấy danh sách xe theo loại hợp đồng"
  Hệ thống làm:
    • Resolve bảng → lấy danh sách cột THỰC TẾ từ PostgreSQL
    • Bơm schema vào prompt → LLM sinh SQL với tên cột có thật
    • Chỉ cho phép SELECT, cấm DDL/DML (an toàn)
  Kết quả: SQL chuẩn dialect, tên cột đúng 100%, có giải thích

ACTION 3 — IMPACT ANALYSIS (Phân tích tác động hạ nguồn)
  Người dùng nói: "Nếu bảng account_use_vehicle đổi schema thì sao?"
  Hệ thống làm:
    • Duyệt đồ thị hạ nguồn (Downstream BFS, tối đa 3 hops)
    • Xác định các bảng staging, DWH, báo cáo BI bị ảnh hưởng
    • Phân loại mức rủi ro: HIGH / MEDIUM / LOW
  Kết quả: "2 báo cáo PowerBI bị ảnh hưởng trực tiếp → Rủi ro: CAO"

ACTION 4 — VISUALIZE LINEAGE (Trực quan hóa dòng chảy dữ liệu)
  Người dùng nói: "Vẽ lineage của bảng account_use_vehicle"
  Hệ thống làm:
    • Lấy toàn bộ upstream + downstream
    • Render đồ thị tương tác (React Flow): kéo thả, zoom, xem chi tiết
    • Mặc định hiển thị văn bản — chỉ vẽ đồ thị khi yêu cầu rõ ràng
  Kết quả: S3 → Glue → account_use_vehicle → Redshift → PowerBI

ACTION 5 — DATA QUALITY CHECK (Kiểm tra chất lượng metadata)
  Người dùng nói: "Kiểm tra chất lượng dữ liệu bảng sourcing_tracker"
  Hệ thống làm:
    • Đánh giá 8 tiêu chí: Schema, Description, Owner, Domain,
      Lineage, Glossary Tags, Custom Tags, Freshness
    • Phân định 6 trạng thái:
      PASS / WARNING / FAILED / MISSING / NOT_AVAILABLE / NOT_EVALUATED
    • Xuất báo cáo PDF hoặc TXT
  Kết quả: "Schema: PASS | Owner: WARNING | Lineage: FAILED"

ACTION 6 — METADATA REPORT (Xuất đặc tả kỹ thuật đầy đủ)
  Người dùng nói: "Xuất đặc tả kỹ thuật của bảng dim_vehicle_account"
  Hệ thống làm:
    • Thu thập toàn bộ: URN, Platform, Domain, Owner,
      danh sách cột (tên + kiểu + mô tả), báo cáo liên quan, lịch sử
    • Định dạng Markdown chuyên nghiệp
    • Xuất PDF/TXT sẵn sàng chia sẻ
  Kết quả: Tài liệu Data Dictionary hoàn chỉnh

SLIDE 7 — CÁCH HỆ THỐNG HIỂU CÂU HỎI
────────────────────────────────────────────────────────────────────────────────

TIÊU ĐỀ:
  Từ "câu hỏi tự nhiên" đến "câu trả lời có căn cứ"

FLOW XỬ LÝ 8 BƯỚC:

  [1] TIỀN XỬ LÝ
      Làm sạch chuỗi, giữ nguyên URN và dot-notation
      "schema bảng   account_use_vehicle!!!" → "schema bảng account_use_vehicle"

  [2] PHÂN LOẠI INTENT
      Regex fast-path + LLM Semantic Classifier
      "schema" → SCHEMA_LOOKUP | "lineage" → LINEAGE | "sql" → GENERATE_SQL

  [3] PHÂN GIẢI THỰC THỂ (Entity Resolution — 4 tầng)
      Tầng 1: Khớp chính xác trong Database
      Tầng 2: Fuzzy Levenshtein (gần đúng, gợi ý nếu nhiều ứng viên)
      Tầng 3: OpenSearch KNN Dense Vector (tìm kiếm ngữ nghĩa)
      Tầng 4: Nhận diện chuỗi URN DataHub hợp lệ
      → "bảng xe" → urn:li:dataset:(...,dms.external.account_use_vehicle,PROD)

  [4] KIỂM SOÁT TRUY CẬP
      Đối chiếu user với entity_acls + rbac_roles
      → Nếu không có quyền: 403 Forbidden

  [5] TRUY XUẤT DỮ LIỆU KÉP
      Structured: Đọc schema/lineage từ PostgreSQL (8–15ms)
      Semantic: Tìm kiếm context bổ trợ từ OpenSearch (35–70ms)

  [6] TỔNG HỢP NGỮ CẢNH
      Đóng gói dữ liệu → Context XML → gửi vào LLM
      LLM chỉ tổng hợp từ context — không suy đoán ngoài phạm vi

  [7] ĐỐI SOÁT DẪN CHỨNG (Citation Grounding)
      Kiểm tra chéo citations với context thực tế
      → Loại bỏ URN không có căn cứ trước khi trả về UI

  [8] GHI VẾT & ĐÁNH GIÁ
      Lưu vào interaction_logs → RAGAS đánh giá → Human Review

VÍ DỤ PHIÊN HỘI THOẠI 4 LƯỢT (thực tế):
  Lượt 1: "Cho tôi xem schema bảng account_use_vehicle"
          → Lưu active_entity = account_use_vehicle
  Lượt 2: "Ai là người sở hữu bảng này?"
          → "bảng này" = active_entity → trả owner
  Lượt 3: "Nó lấy dữ liệu từ đâu?"
          → "Nó" = active_entity → 1 upstream: AWS Glue
  Lượt 4: "Còn bảng sourcing_tracker thì sao?"
          → Chuyển active_entity sang sourcing_tracker

LỚP 3 — KIỂM SOÁT CHI TIẾT (Entity ACL — 884 quy tắc)
  • Bộ lọc ACL áp dụng TRỰC TIẾP tại mức SQL WHERE clause:
    WHERE domain IN ('Logistics', ...) OR entity_urn IN (allowed_urns)
  • Đồng thời áp dụng OpenSearch Bool Filter
  • LLM KHÔNG nhận được siêu dữ liệu ngoài quyền hạn

CƠ CHẾ BẢO VỆ BỔ SUNG:
  • Prompt Injection Detection: Từ chối lệnh cố ý phá vỡ system prompt
  • Secret Masking: Tự động ẩn mật khẩu, API keys, connection strings
  • SQL Safety: Chỉ cho phép SELECT, cấm DDL (DROP, ALTER) và DML
